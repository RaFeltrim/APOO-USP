Padrão de Projeto Observer

Padrão Comportamental — Gang of Four (GoF)

Disciplina: SSC0124 — APOO Aluno: Rafael Feltrim Data: Agosto/2026

1. Propósito do Padrão

O Observer é um padrão de projeto comportamental que permite definir um mecanismo de assinatura para notificar múltiplos objetos sobre quaisquer eventos que aconteçam com o objeto que eles estão observando.

O padrão Observer, também conhecido como Observador, Event-Subscriber ou Listener, estabelece uma relação um-para-muitos entre objetos, de modo que quando um objeto (o "sujeito" ou "publicador") muda de estado, todos os seus dependentes (os "observadores" ou "assinantes") são automaticamente notificados e atualizados.

Este padrão pertence à categoria dos padrões comportamentais do catálogo GoF, sendo um dos 23 padrões originais documentados por Erich Gamma, Richard Helm, Ralph Johnson e John Vlissides em 1995.

2. O Problema que o Padrão Resolve

Imagine um cenário com dois tipos de objetos: um Cliente e uma Loja. O cliente está interessado em um produto que em breve estará disponível na loja. Há duas abordagens ingênuas para resolver este problema:

2.1. Abordagem por Polling

O cliente visita a loja todos os dias para verificar a disponibilidade do produto. Enquanto o produto não chega, a maioria dessas visitas será em vão, gerando desperdício de tempo e recursos.

2.2. Abordagem por Notificação em Massa (Spam)

A loja poderia enviar emails para todos os clientes cada vez que um novo produto se torna disponível. Isso economizaria viagens dos clientes interessados, mas irritaria clientes que não estão interessados naquele produto específico.

Problema central: Ou o cliente gasta tempo verificando a disponibilidade, ou a loja gasta recursos notificando os clientes errados. Existe um conflito entre eficiência e relevância da comunicação.

Em termos de software, este problema se manifesta quando:

  • Um objeto precisa informar outros sobre mudanças em seu estado, mas não sabe quem são (ou quantos são) esses objetos.
  • O acoplamento direto entre classes torna o sistema rígido e difícil de estender.
  • Novos "observadores" precisam ser adicionados sem modificar o código da classe observada.

3. A Solução Proposta

O padrão Observer propõe um mecanismo de assinatura (subscription mechanism) que resolve o problema de forma elegante:

3.1. Conceitos-chave

  • Publicador (Publisher/Subject): O objeto que possui um estado interessante e emite notificações quando esse estado muda.
  • Assinante (Subscriber/Observer): Os objetos que desejam ser informados sobre mudanças no publicador.
  • Interface do Assinante: Uma interface comum que todos os assinantes devem implementar, garantindo que o publicador se comunique com eles de forma desacoplada.

3.2. Mecanismo

O mecanismo consiste em:

  1. Uma lista (vetor) para armazenar referências aos objetos assinantes.
  2. Métodos públicos subscribe() e unsubscribe() para adicionar e remover assinantes.
  3. Um método notify() que percorre a lista e chama o método update() em cada assinante.

3.4. Exemplo em Java — Sensor de Temperatura

Interfaces:

public interface Observer {
    void update(float temperatura);
}

public interface Subject {
    void addObserver(Observer o);
    void removeObserver(Observer o);
    void notifyObservers();
}

Publicador concreto:

public class SensorTemperatura implements Subject {
    private List<Observer> observers = new ArrayList<>();
    private float temperatura;

    public void addObserver(Observer o) {
        observers.add(o);
    }

    public void removeObserver(Observer o) {
        observers.remove(o);
    }

    public void notifyObservers() {
        for (Observer o : observers)
            o.update(temperatura);
    }

    public void setTemperatura(float t) {
        this.temperatura = t;
        notifyObservers();  // notifica automaticamente
    }
}

Assinantes concretos:

public class DisplayCelsius implements Observer {
    public void update(float temp) {
        System.out.println("Display: " + temp + "°C");
    }
}

public class AlertaCalor implements Observer {
    public void update(float temp) {
        if (temp > 40)
            System.out.println("⚠️ ALERTA: " + temp + "°C!");
    }
}

Uso (Main):

public class Main {
    public static void main(String[] args) {
        SensorTemperatura sensor = new SensorTemperatura();

        sensor.addObserver(new DisplayCelsius());
        sensor.addObserver(new AlertaCalor());

        sensor.setTemperatura(25.0f);
        // Saída: Display: 25.0°C

        sensor.setTemperatura(42.0f);
        // Saída: Display: 42.0°C
        //        ⚠️ ALERTA: 42.0°C!
    }
}

4. Quando Aplicar o Padrão

4.1. Cenários de Aplicação

  • Mudanças em cascata: Quando mudanças no estado de um objeto precisam atualizar outros objetos, e o conjunto de objetos é desconhecido de antemão ou muda dinamicamente.
  • Interfaces gráficas: Botões, campos de texto e outros componentes de GUI que precisam notificar listeners quando eventos ocorrem (cliques, digitação, etc.).
  • Observação temporária: Quando objetos devem observar outros apenas por um tempo limitado ou em casos específicos — a lista de inscrição é dinâmica.
  • Arquiteturas dirigidas a eventos: Sistemas de mensageria, event buses, e arquiteturas pub/sub.
  • Desacoplamento: Quando você quer que o emissor de eventos não conheça as classes concretas que reagem a eles.

5. Prós e Contras

👍 Prós

  • Princípio Aberto/Fechado (OCP): Novas classes assinantes podem ser introduzidas sem modificar o código da publicadora, e vice-versa.
  • Relações dinâmicas em runtime: Assinantes podem entrar e sair da lista a qualquer momento durante a execução do programa.
  • Baixo acoplamento: O publicador conhece os assinantes apenas pela interface, não pelas classes concretas. Isso promove a extensibilidade.
  • Reutilização: O mecanismo de eventos pode ser extraído para uma classe auxiliar e reutilizado em qualquer publicador.

👎 Contras

  • Ordem não determinística: Assinantes são notificados em ordem aleatória (ou na ordem de registro), sem garantia de sequência.
  • Risco de memory leaks: Se assinantes não forem explicitamente removidos, o publicador mantém referências que impedem o garbage collector.
  • Complexidade de depuração: O fluxo de controle pode ser difícil de rastrear quando há muitos assinantes e eventos encadeados.
  • Atualizações em cascata: Uma notificação pode desencadear outras notificações, criando potenciais ciclos ou comportamentos inesperados.

6. Relações com Outros Padrões

Padrão Relacionado Relação
Mediator O Mediator elimina dependências múltiplas via um objeto central. O Observer estabelece comunicação de uma via dinâmica. Um Mediator pode ser implementado usando Observer internamente.
Command O Command encapsula uma requisição como objeto. Pode ser combinado com Observer: um comando é executado em resposta a uma notificação.
Chain of Responsibility Ambos conectam remetentes e destinatários. No CoR, o pedido segue uma cadeia sequencial. No Observer, a notificação vai para todos os inscritos simultaneamente.
Strategy Ambos usam composição e interfaces. Strategy permite trocar algoritmos; Observer permite reagir a eventos. São complementares.

7. Conexão com Princípios SOLID

  • S — Single Responsibility: O publicador se preocupa com sua lógica de negócio; a gestão de assinantes pode ser delegada a uma classe auxiliar (ex: EventManager).
  • O — Open/Closed: O principal benefício. Novos assinantes são adicionados sem modificar o publicador.
  • D — Dependency Inversion: O publicador depende da abstração (interface Subscriber), não de implementações concretas.
