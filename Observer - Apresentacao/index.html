01

Definição do Padrão

O Observer é um padrão de projeto comportamental que estabelece uma dependência um-para-muitos entre objetos, de forma que quando um objeto muda de estado, todos os seus dependentes são notificados e atualizados automaticamente.

Publicador (Subject)

Objeto que detém o estado principal e gerencia a emissão de notificações sobre suas alterações.

Assinante (Observer)

Objetos dependentes que se registram para receber notificações quando o estado do Publicador for alterado.

02

O Problema

Considere a necessidade de manter consistência entre objetos relacionados sem criar acoplamento forte.

Abordagem 1: Polling Constante

O objeto dependente verifica o estado do objeto principal periodicamente.

Desperdício considerável de recursos computacionais, pois a maioria das verificações não resulta em alterações.

Abordagem 2: Notificação em Massa

O objeto principal notifica indiscriminadamente todos os outros objetos do sistema a cada mudança.

Sobrecarga de comunicação e processamento em objetos que não têm interesse na alteração.

Dilema: Como notificar apenas os objetos interessados, no momento exato da alteração, sem que o emissor precise conhecer a classe concreta dos receptores?

03

A Solução Proposta

O padrão introduz um mecanismo estruturado de inscrição (Publish-Subscribe):

1. Inscrição

Objetos Observers anexam-se ao Subject através de um método público.

2. Alteração de Estado

O Subject sofre uma modificação em seu estado interno.

3. Notificação

O Subject itera sobre sua lista de inscritos, invocando um método comum de atualização.

Elementos Arquiteturais Fundamentais

  • O Subject mantém apenas uma lista de referências abstratas (interfaces).
  • Métodos de gerenciamento: attach() e detach().
  • Os Observers implementam uma interface comum contendo o método update().
04

Contextualização Abstrata

Analogia: Assinatura de Periódicos

Em vez de um leitor visitar a banca diariamente para verificar se uma nova edição foi lançada (Polling), ele realiza uma assinatura.

A editora mantém um registro de assinantes e, assim que a edição é publicada, a distribui ativamente para os endereços registrados.

O assinante pode cancelar o serviço (unsubscribe) a qualquer momento, removendo-se da lista.

Mapeamento Estrutural

Editora → Subject (Publicador)
Lista de Endereços → Estrutura de Dados (Coleção)
Leitores Inscritos → Observers (Assinantes)
Entrega da Edição → Método update()

06

Implementação (Java) — Estrutura Base

// Interfaces que estabelecem o contrato de comunicação
public interface Subject {
    void attach(Observer observer);
    void detach(Observer observer);
    void notifyObservers();
}

public interface Observer {
    void update(float temperature);
}
public class WeatherStation implements Subject {
    private List<Observer> observers = new ArrayList<>();
    private float temperature;

    public void attach(Observer o) { observers.add(o); }
    public void detach(Observer o) { observers.remove(o); }

    public void notifyObservers() {
        for (Observer o : observers) {
            o.update(temperature);
        }
    }

    public void setTemperature(float t) {
        this.temperature = t;
        notifyObservers(); // Propaga a mudança
    }
}
public class TemperatureDisplay implements Observer {
    private String displayName;

    public TemperatureDisplay(String name) {
        this.displayName = name;
    }

    public void update(float temperature) {
        System.out.println(displayName + ": Atualização de temperatura -> " + temperature + "°C");
    }
}
07

Aplicabilidade

Cenários Indicados

  • Quando a alteração no estado de um objeto exige a modificação de outros, e o conjunto de dependentes é desconhecido ou dinâmico a tempo de execução.
  • Quando uma abstração possui dois aspectos onde um depende do outro. Encapsular esses aspectos em objetos separados permite sua variação e reutilização independentes.
  • Quando é necessário estabelecer comunicação entre componentes sem introduzir acoplamento rígido (Princípio da Inversão de Dependência).

Contraindicações

  • Quando o fluxo de notificação é rigorosamente sequencial (padrões como Chain of Responsibility são mais adequados).
  • Quando a quantidade de observadores é estática e estritamente limitada, tornando a infraestrutura de eventos desnecessária.
08

Análise Crítica

Vantagens (Prós)

  • Acoplamento Abstrato: O Subject conhece os Observers apenas através de uma interface abstrata.
  • Suporte a Broadcast: A notificação é enviada a todos os objetos inscritos nativamente.
  • Princípio Aberto/Fechado (OCP): É possível introduzir novas classes de assinantes sem modificar o código do publicador.

Desvantagens (Contras)

  • Atualizações Inesperadas: Como os observadores não se conhecem, o custo de uma alteração de estado pode ser alto.
  • Ordem não Determinística: A ordem na qual os observadores são notificados geralmente não é garantida.
  • Vazamento de Memória: A falha em desregistrar observadores (Lapsed Listener Problem) retém objetos na memória.
09

Considerações Finais

Observer vs. Mediator

Enquanto o Mediator centraliza o fluxo de comunicação encapsulando as interações em um objeto gestor, o Observer distribui a comunicação dinamicamente, conectando emissores e receptores através de interfaces.

Uso Típico em Arquitetura de Software

O Observer é a fundação para arquiteturas reativas (Reactive Programming), arquiteturas orientadas a eventos (Event-Driven Architecture) e o tradicional padrão MVC (Model-View-Controller), no qual a View atua como Observer do Model.

O Padrão Observer demonstra o poder das interfaces em isolar responsabilidades. Ao promover um acoplamento mínimo entre emissores e receptores, tornou-se essencial para a construção de sistemas distribuídos, processamento de eventos e interfaces gráficas responsivas na engenharia de software moderna.
